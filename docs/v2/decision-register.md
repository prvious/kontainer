# Kontainer v2 consolidated decision register

Status: historical architecture audit; partially superseded  
Audit date: 2026-08-19  
Scope: cross-report decisions, conflicts, prerequisites, and deferrals for the Rust rewrite

> **Superseding approval (2026-08-23):** [The greenfield Rust reset](./approved-greenfield-reset.md) is now authoritative. It replaces conflicting candidates involving Go coexistence, SQLite, `/api/v2`, SSE, legacy adapters, v1 data migration/parity, framework-free Axum composition, custom TOML, and deferred ARM64. Rows below are frozen historical research. Their old `open`, `accept`, or `provisional` labels are not implementation blockers where the approved reset resolves the subject; new decisions extend the approved reset instead of trying to retrofit every historical row.

## Purpose and authority

This register consolidates the decisions in the completed v2 reports and resolves their cross-domain disagreements. It does not repeat every endpoint, field, state transition, test case, or route-local limit; those remain owned by the linked domain report. Its purpose is to give implementation work one stable place to answer:

- whether a choice is accepted, provisional, open, deferred, or rejected;
- which profile or milestone a choice belongs to;
- which open choice blocks downstream work;
- which report is authoritative when two reports use different language.

For subjects not resolved by the approved reset or a later ADR, an `accept` row means the completed reports already converge on that choice, while an `open` row remains a product or architecture blocker. A `provisional` row is the recommended implementation default but must be ratified or replaced using the named evidence. `defer` means the core design must leave an extension seam but the feature is outside the current gate. `reject` means no compatibility mode may introduce the route into production without a new ADR.

The audit covered all current reports: [API/protocol](./api-protocol.md), [cluster communication](./cluster-communication.md), [exec](./exec.md), [logging](./logging.md), [metrics/storage](./metrics-storage.md), [observability](./observability.md), [performance](./performance.md), [reliability/testing](./reliability-testing.md), [Rust architecture](./rust-architecture.md), [security](./security.md), [stack deployment](./stack-deployment.md), [Swarm resources](./swarm-resources.md), and [agent lifecycle](./agent-lifecycle.md), plus the repository rules in [`CLAUDE.md`](../../CLAUDE.md).

## Milestone vocabulary

The reports currently use “parity,” “MVP,” “beta,” “production v2,” and “GA” inconsistently. This register uses the following meanings pending approval of ADR-CAND-001:

| Milestone | Meaning |
|---|---|
| **Parity** | Existing user-visible v1 workflows on the explicitly non-HA embedded profile, with mandatory security, correctness, bounded-resource, and honesty repairs. It does not include features absent from v1 merely because an old UI implied them. |
| **Feature MVP** | The first usable slice of a new domain, such as Compose stack deployment or metrics rollups. It is not a product release tier. |
| **Beta** | Production-shaped three-manager/controller testing with the shared control store, leases/claims, automated identity lifecycle, migration/restore, signed artifacts, and medium soak/chaos evidence. |
| **GA** | Every capability advertised by the release has passed its supported topology, storage, Engine, architecture, upgrade, security, SLO, canary, and disaster-recovery gates. The HA profile cannot use SQLite. |
| **Later** | An explicitly absent capability advertised as unsupported, not an empty endpoint or implied promise. |

## Conflict and dependency audit

| Conflict or hidden expansion | Resolution | Downstream effect |
|---|---|---|
| Embedded SQLite is called the MVP default while production reports require multiple controllers and shared state. | Use named profiles: embedded single-controller dual-SQLite is supported but non-HA; HA uses a shared transactional control store and a shared/routed metrics store. See ADR-CAND-029, ADR-CAND-030, and ADR-CAND-031. | The GA/HA marketing claim and production database selection remain product blockers. Domain ports can be built before the backend is selected. |
| Reports variously say one controller, one per manager, at least three replicas, or a fixed odd replica count. | Global-on-managers is the recommended production default; a fixed spread replica set is an explicit alternative. There is no application leader for public requests; only singleton work is leased. See ADR-CAND-004 and ADR-CAND-032. | Production manifests, ingress, failure tolerance, and large-profile budgets wait for placement approval. |
| The exec report allows a manager-local exec actor in the controller, but cluster/security/lifecycle require all node-local work to use the node agent. | Every exec, including a target on a manager, goes through that node's node-agent task. See ADR-CAND-023. | Prevents controller/node-agent privilege duplication and makes local and remote behavior test-identical. The exec diagram and future implementation must follow this register. |
| Rust architecture broadly assigns logs to node core, while logging and cluster reports use manager-native service/task logs. | The controller owns Swarm service/task log sources through its manager Engine. Node agents own only the separately authorized local-container fallback, which is deferred. See ADR-CAND-024 and ADR-CAND-055. | Avoids an unnecessary N-task follower fan-out and a controller-core/node-core responsibility collision. |
| API, security, logging, and exec differ on Authorization headers, one-time tickets, query parameters, subprotocol values, and whether failure occurs before upgrade. | Native Authorization-header WSS is primary. A fallback ticket is never in a URL or subprotocol; it is the only allowed first binary frame after a tightly limited unauthenticated upgrade. Ticket failure therefore closes after upgrade; only origin/rate/protocol admission can fail before `101`. See ADR-CAND-021. | Stream handlers and tests must not promise that a first-frame ticket replay fails before upgrade. The long-lived JWT query path is forbidden. |
| API polling returns a token from `GET`, while security uses a separate `POST` redemption transaction. | `GET` may report pending/ready state but never returns credentials. `POST /api/v2/auth/sessions/{id}/redeem` exchanges the verifier and one-time result for tokens. See ADR-CAND-016. | Prevents unsafe retry/cache semantics and closes route naming before client generation. |
| API leaves opaque versus JWT access tokens open, while security specifies asymmetric access JWTs. | Human access tokens are short-lived asymmetric JWTs; refresh and service tokens are opaque and server-state-backed. See ADR-CAND-017. | Token format is no longer an API blocker; algorithm/KMS profile remains open. |
| Repository rules require `session.json`, while all v2 security/client reports require OS-vault custody and no bearer in React. | The v2 architecture requires an explicit repository-rule change and a tested migration before desktop auth implementation. See ADR-CAND-018. | This is a hard governance blocker for v2 desktop credential code; it must not be bypassed by silently continuing plaintext storage. |
| A reusable client is required to support Tauri, GPUI, and CLI, which can be read as requiring a GPUI rewrite for parity/GA. | Tauri remains the shipping desktop baseline. The client crate is UI-framework-neutral; a small GPUI test host is optional evidence, not a product UI or parity gate. See ADR-CAND-009 and ADR-CAND-052. | Prevents a hidden desktop rewrite from entering the server rewrite scope. |
| Metrics reports differ on pull versus push, 60 versus 30 seconds, oldest versus “newest-first” replay, retention, and coverage SLOs. | Parity may collect every 60 seconds; the benchmark-gated v2 default is 30 seconds. Agents push retained batches in ascending sequence; overflow drops the oldest and reports the lost interval. Retention tiers are data-class-specific. Public coverage is provisionally 99% per five-minute window; 99.9% remains an internal healthy-connected target. See ADR-CAND-025 through ADR-CAND-028. | The 30-second default, disk limits, exact retention, and supported envelope cannot become GA claims until the metrics benchmark is accepted. |
| Operation records, stack journals, observability history, audit records, idempotency records, and diagnostic logs risk becoming competing truths. | One control-store transaction owns operation admission, idempotency, ordered operation/step state, and required audit intent before dispatch. Stack steps extend the general operation model. Audit is a separate append-only chain and external anchor; diagnostic telemetry is never authoritative. See ADR-CAND-034. | Eliminates duplicate state machines and makes crash recovery and partial-result accounting testable. |
| Health paths are `/health/live` and `/health/ready` in the API report but `/livez`, `/startupz`, and `/readyz` in lifecycle/observability. | Canonical process probes are `/livez`, `/startupz`, and `/readyz`; legacy and draft spellings may be exact aliases during migration and must use the same state owner. See ADR-CAND-014. | OpenAPI and deployment probes must not implement independent health logic. |
| Internal compatibility alternates between previous minor, previous major, and N/N-1 release. | Provisional rule: both controller/agent orientations interoperate across adjacent product releases within protobuf major `v2`; no N-1 protocol-major promise. See ADR-CAND-033. | Must be approved before protobuf fields, code generation, and rolling-upgrade CI stabilize. |
| The Swarm report calls stack deploy a missing parity affordance, while the stack report says strict parity has no Compose deployment requirement. | Stack list/removal are parity; deployment is a separate feature MVP. The reconciler design is accepted for when that capability ships, but it is not silently added to the parity gate. See ADR-CAND-037 and ADR-CAND-038. | Product must decide whether stack deployment is in the first GA capability set; core Rust work need not wait. |
| Stream and response limits disagree: 64 KiB WebSocket messages versus 256 KiB Docker log records, 1 versus 2 MiB log queues, four versus ten exec sessions per principal, and 2/5/8 MiB JSON ceilings. | Decode large upstream records incrementally and fragment to at most 64 KiB protocol messages. Start with the stricter 1 MiB public log-session queue and four exec sessions per principal. Use 2 MiB normal collection pages, a 5 MiB metrics-series route exception, and an 8 MiB absolute JSON ceiling. See ADR-CAND-043. | All values remain provisional and discoverable; load evidence, not library defaults, changes them. |
| `kontainer-stack` is shown depending on controller core, while controller actions also need the stack reconciler, creating a likely crate cycle. | Stack domain, parser, planner, and reconciler own their ports in `kontainer-stack-core` (name illustrative). Controller composition depends on it; the stack crate must not import controller core. See ADR-CAND-007. | Prevents a Cargo dependency cycle before crate layout hardens. |

## Decisions required before the first production Rust code

Time-boxed spike code may precede these decisions when a report explicitly requires evidence. Production implementation should not begin until the following are approved:

1. **ADR-CAND-001, ADR-CAND-002, and ADR-CAND-079:** milestone/profile names, GA/HA claim, workspace location, Go coexistence, toolchain/MSRV/license, and the approval boundary for dependencies.
2. **ADR-CAND-003 through ADR-CAND-007:** two binaries, controller/node authority, and acyclic crate/dependency direction. In particular, no controller-local exec path and no node-owned Swarm service log path.
3. **ADR-CAND-012, ADR-CAND-013, ADR-CAND-016, ADR-CAND-021, ADR-CAND-033, and ADR-CAND-066:** protocol families, type boundaries, auth redemption, ticket behavior, compatibility unit, and generation authority before wire types spread.
4. **ADR-CAND-018:** repository approval for native vault custody before any v2 desktop session implementation.
5. **ADR-CAND-019:** capability names and a minimum role/scope matrix before handlers or migrations encode authorization assumptions.
6. **ADR-CAND-029, ADR-CAND-030, ADR-CAND-034, and ADR-CAND-078:** named storage profiles, one selected SQLite access path, migration ownership, and the atomic operation/idempotency/audit-intent contract before persistence schemas or mutations are written. The exact PostgreSQL topology may remain open behind ports.
7. **ADR-CAND-045:** internal identity/SAN/delegation model and test PKI before an internal RPC implementation. Production issuer choice ADR-CAND-046 may follow, but no plaintext/shared-secret stepping stone may ship.
8. **ADR-CAND-048:** either ratify API 1.41/Linux as the initial Engine floor or explicitly label it provisional in adapter fixtures before resource code begins.

Dependency changes remain separately subject to repository approval. The required Rust spikes in [Rust architecture](./rust-architecture.md#required-dependency-spikes-before-commitment) are evidence-generating work, not implicit permission to commit their candidate crates.

## Decisions safe to defer from initial core work

The following do not block the workspace, pure domain/action code, protocol fixtures, fake Engine, or embedded-profile parity as long as their ports/capabilities remain explicit:

- the final PostgreSQL/HA metrics implementation (ADR-CAND-031), controller ingress alternative (ADR-CAND-032), and external audit anchor product (ADR-CAND-041), although all are required before their production claims;
- production CA/KMS/FIPS integrations (ADR-CAND-046 and ADR-CAND-047) when protocol work uses a test PKI and the accepted identity model;
- exact performance/SLO/RPO/RTO and canary numbers (ADR-CAND-049 and ADR-CAND-051), which require measured evidence;
- stack deployment inclusion and parser choice (ADR-CAND-039), provided stack list/removal parity stays separate;
- GPUI product UI, native services, Windows/other platforms, local-container log fallback, detachable exec, remote/NAT transport, extra metrics stores, GitOps/build features, and advanced security profiles (ADR-CAND-052, ADR-CAND-055, ADR-CAND-056, ADR-CAND-061 through ADR-CAND-063, and ADR-CAND-065);
- optional public encodings/protocols and IPC generators (ADR-CAND-059).

## Approval rule

Every `open` or `provisional` row should become a short owned ADR or issue with a decision date, selected option, rejected alternatives, migration impact, and verification evidence. When approved, preserve the ADR-CAND ID and change only its status/decision text; do not renumber the register. A downstream implementation issue must list the IDs it depends on, and may not close while a blocking ID remains `open`.

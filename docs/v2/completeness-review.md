# Kontainer v2 completeness review

Status: final cross-report completeness audit  
Review date: 2026-08-19  
Scope: all reports in `docs/v2`, the repository instructions, the 411 stable V1 traceability items, and the 12 unresolved V1 archaeology questions

Post-audit update: [the feature ledger](./feature-ledger.md) now resolves the mechanical coverage blocker below with exactly 411 unique stable rows and 12 separate question rows. The desktop/profile, backend-only surface, configuration/data migration, UI disposition, and historical resource-editor decisions identified by this review remain open and are intentionally marked `decision-blocked` in that ledger.

## Executive finding

At audit time, the report set was **domain-complete but not yet traceability-complete**. The later feature ledger closes the missing row-by-row mapping, while its `decision-blocked` rows preserve the unresolved product and contract choices rather than guessing them. Every requested domain has a plausible v2 owner and a meaningful verification strategy. The resource, lifecycle, security, streaming, storage, release, observability, and test designs are unusually thorough. No new subsystem is required to cover setup/auth/health, schedules, discovery, Swarm resources, operations, metrics, logs, exec, release, observability, or testing.

What is still missing is mechanical closure from the V1 inventory to those designs. The reports provide family-level ownership and broad parity gates, but there is no row-by-row disposition ledger for all 411 stable IDs. The two existing gates are narrower: [API/protocol](./api-protocol.md#v1-audit-and-parity) requires an owner decision for routes and RPCs, while [reliability/testing](./reliability-testing.md#gate-1-v1-visible-parity) requires normalized scenarios for desktop-visible workflows. That leaves backend-only surfaces, local desktop behavior, configuration keys, persistence scaffolding, placeholders, historical work, and evidence-only items without a mechanically checkable terminal outcome.

Three issues had to be closed before the synthesis could claim complete V1 coverage. The first is now complete; the latter two remain decision work:

1. **Completed after this audit:** add the item-level disposition/acceptance ledger described below.
2. Resolve the desktop credential/profile migration blocker in ADR-CAND-018 together with profile identity and switching semantics from V1-Q-006.
3. Freeze whether backend-only agents, live stats, and controller settings are parity, diagnostics, or removed surfaces, then finish the typed settings/config migration contract in ADR-CAND-068/069/078.

The [decision register](./decision-register.md) is already the right authority for cross-report conflicts. Several source reports, however, still contain superseded instructions. Those conflicts need visible errata or an explicit normative-precedence statement so an implementation issue cannot accidentally follow the older text.

## Uncovered or under-specified items

### Blocker

1. **No item-level closure for the 411 stable V1 IDs.** Family reports and broad gates cannot prove that every ID was consciously migrated, fixed, kept legacy-only, archived, deferred, or rejected. This is the main completeness blocker. Create a checked master ledger with columns: `V1 ID`, v1 classification, v2 disposition, milestone/profile, normative owner, replacement contract/action, acceptance scenario or evidence-only rationale, migration/release-note effect, dependent ADR, and status. Require exactly one row per stable ID; link all 12 `V1-Q-*` questions to a decision or an explicitly open blocker.

2. **Desktop credential/profile migration is blocked and semantically incomplete.** ADR-CAND-018 correctly identifies the repository-rule conflict, but `V1-PROFILE-001–007`, `DATA-008–009`, and `IPC-003–009` also need a single profile state model. Select the uniqueness key from V1-Q-006 and specify duplicate login, startup validation, URL edits, refresh failure, inactive expiry, active deletion, vault rollback, query-client replacement, old-stream closure, logout/revocation, and crash-safe plaintext cleanup. The existing broad “profile restore/switch/logout” test wording is not enough to settle these races.

3. **The parity status and contract of backend-only surfaces are not frozen.** `HTTP-013`, `HTTP-024`, `HTTP-048–049`, `DTO-002/007/018`, `IPC-010/047–048`, `UI-016`, and `GAP-012/016` are described variously as backend-only, strict visible parity, accepted baseline, diagnostics, or unfinished UI. The API strict-parity paragraph also says “inspect secrets,” although v1 has no secret-inspect route and the API route matrix does not add one. Decide each surface explicitly. If live task stats map to `/metrics/snapshot`, state the field/identity/freshness mapping. If settings remain, ADR-CAND-068 must enumerate the typed schema before OpenAPI or migration freezes. If a surface is diagnostics-only or removed, give it a capability/legacy and release-note outcome.

4. **The first-upgrade data/config contract is not executable yet.** ADR-CAND-047/068/069/078 openly block encryption, settings/config DTOs, legacy adapter/data outcomes, and storage/migration ownership. Lifecycle promises v1 import, but no artifact maps every active config key and every v1 data class to copy, transform, archive, discard, or operator replacement. The migration plan must include source-schema variants, profile/vault ordering, provider/signing secret conversion, settings conversion, unified and legacy metrics outcomes, queue/scaffold retirement, rollback window, count/checksum report, and the exact point at which the preserved v1 source may be deleted.

### High

1. **Configuration compatibility is only schema-level, not key-level.** Add a 70-row appendix or grouped exhaustive table. Pay particular attention to `DOCKER_HOST`, `DOCKER_TLS_VERIFY`, `DOCKER_CERT_PATH`, and `DOCKER_API_VERSION`: v1 treated them as useful inputs, Rust architecture exposes possible remote-rustls support, while ADR-CAND-077 recommends local socket only for baseline. Also map `HOST_PROC`, bind/base URL, metrics interval/retention, DB paths, logging outcomes, TLS, build/fixture-only inputs, and removed Goravel scaffolding.

2. **Frontend labels hide unbudgeted backend scope.** Produce an explicit `V1-UI-*` disposition table. At minimum:
   - network I/O requires new metric families, transport/storage/query fields, DTOs, and charts; it is not merely a chart fix;
   - service ports are resource DTO/UI work, separate from network metrics;
   - Docker version, agent version/uptime, WSS status, and stream count span build metadata, capability/observability data, native-client session state, and UI;
   - stack CPU/memory needs a defined stack-to-service aggregation and completeness policy, not the stack reconciler;
   - filters/sorts require per-screen semantics over the API cursor/sort contract;
   - exec PID/TTY depends on ADR-CAND-074 and truthful Engine/session metadata;
   - agent settings require the backend-only surface decision above.

3. **The unmerged service-resource editor is orphaned.** `V1-HIST-007` and V1-Q-001 need a product disposition. Stack deployment's Compose model supporting resource limits does not decide whether standalone service resource patching/editor behavior is parity, an enhancement, or rejected. Add a decision-register row and a route/UI/test consequence.

4. **Several accepted cross-report decisions are not propagated to their source reports.** An implementer reading only a domain report can still build the wrong actor, auth flow, queue limits, replay order, health paths, or rollout order. Treat the errata table below as a required synthesis amendment, not editorial cleanup.

5. **Local preferences and desktop-shell outcomes lack exact acceptance.** `DATA-010/013`, `IPC-049–051`, `BUG-021`, and `SCR-017` have a correct architectural boundary but no complete retained/migrated behavior. Specify settings schema/version and per-field fallback, partial-write behavior, theme/native-scheme ownership, window-state outcome, splash lifecycle, and tests. Purely visual styling can remain frontend-only; persistence and lifecycle cannot.

6. **The route-replacement matrix is not fully normalized.** The synthesis should publish one final matrix containing canonical probes, auth redemption, backend-only decisions, nested-alias removals, live stats mapping, settings, and optional ticket endpoints. Current API prose and table are internally superseded by ADR-CAND-014/016/021 in several places.

### Medium

1. **Evidence-only and obsolete items still need terminal ledger entries.** `FIX-*`, `TEST-*`, framework-only `CFG-*`, queue tables, old HTTP discovery, and removed metric tables should be explicitly marked “evidence only,” “fixture replaced,” “archive/discard,” or “rejected.” Generic statements are adequate architecture but not adequate traceability.

2. **Screen parity should name removed placeholders.** Normalized `SCR-*` scenarios should assert that fake cards/no-op buttons are removed or capability-disabled, rather than merely omitting them. This avoids a later UI pass restoring false status.

3. **Agent/build status presentation needs one source-of-truth statement.** Observability and runtime metadata can provide build version/start time; native client state can provide connection/stream state. State which values are server facts versus client facts and keep branch names out unless release provenance actually supplies them.

4. **Metrics and prune controls need explicit UI acceptance.** `GAP-016` is not a transport gap after the v2 route designs, but the parity scenarios should state whether range/step and per-node prune selection are exposed, defaulted, or intentionally omitted from the desktop.

5. **Aspirational settings language needs splitting.** `ASP-007` combines per-profile refresh/customization, theme control, and agent YAML editing. The first two are desktop-local; typed controller settings are remote product data; raw agent configuration editing is rejected by the strict operator-config boundary unless a future typed workflow is approved.

## Concrete amendments for the root synthesis

1. **State normative precedence.** Say explicitly: approved ADRs, then the consolidated decision register, then the owning domain report; where the register lists a conflict, the older domain text is superseded. Include the errata table above or direct links to it.

2. **Add the complete V1 traceability appendix.** Require exactly 411 stable rows plus 12 question rows. Do not allow a family-level checkmark to close an item. A behavior requiring no runtime implementation still needs an evidence-only, archive, defer, or reject row and rationale.

3. **Widen the parity release gate.** Keep normalized executable scenarios for user-visible behavior, but make Gate 1 also validate that every stable V1 ID has a terminal ledger disposition and acceptance evidence appropriate to its class. API's route/RPC fixture requirement becomes one subset, not the whole ledger.

4. **Publish one final parity boundary.** Preserve current user workflows and existing useful backend contracts only when deliberately selected. Explicitly exclude service creation, node join, network/volume lifecycle, image pull, Compose deployment, host shell, and other old no-op affordances from parity per ADR-CAND-037. Resolve agents/live stats/settings/secret inspect and `HIST-007` rather than leaving them implicit.

5. **Publish one final route/protocol replacement matrix.** Use canonical `/livez`, `/startupz`, `/readyz`; possession-bound `POST .../redeem`; canonical task collections; explicit `/tasks/stats` replacement; typed settings decision; native WSS header auth and first-frame ticket fallback only; and no URL credentials or duplicate nested aliases.

6. **Add a desktop/profile/local-state contract.** Resolve ADR-CAND-018 and V1-Q-006, then specify profile state transitions, secure-store migration, query/client identity, stream teardown, URL edit behavior, logout/revocation, local settings, window state, and splash acceptance. Link each relevant `DATA`, `IPC`, `PROFILE`, `BUG`, `SCR`, and `GAP` ID.

7. **Add exhaustive configuration and data migration maps.** For configuration, map all `CFG-001–070` items to new key/source or a terminal retirement class. For data, map every `DATA-*` class and schema variant to copy/transform/archive/discard/replacement, with checksums, backup, rollback, and deletion criteria. Call out that remote Docker support is not baseline unless ADR-CAND-077 selects it.

## Final assessment

No requested technical area needs a new architecture report. Setup/auth/health, schedules, agent discovery, resource locality, task churn, durable operations, metrics, logs, exec, release, observability, and the test strategy are all substantively covered. Settings, configuration migration, desktop/profile/local state, backend-only surfaces, and historical/UI dispositions remain incomplete at the contract or traceability level.

The root synthesis can accurately describe the research as comprehensive once it distinguishes **architectural coverage** from **closed parity traceability**. It should not claim the latter until the full ledger, desktop/profile contract, backend-only route decisions, and migration maps exist.
